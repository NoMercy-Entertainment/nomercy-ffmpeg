# stemsplit 1.1.0 release gates — design

**Date:** 2026-10-31
**Trigger:** ffmpeg-stemsplit 1.1.0 is released as tag `v1.1.0`. `scripts/60-stemsplit.sh`
takes the newest release, so the next nomercy-ffmpeg build carries it. The handover
(`docs/handover-1.1.0.md` in the stemsplit repository, section "nomercy-ffmpeg") and the
contract (`2026-09-28-stemsplit-roformer-contract-design.md`, §7 rule 7 and the §8 CI row)
say what this repository's CI must prove **before a release carries 1.1.0 to users**:

1. the tiny RoFormer models on every platform: scheduler, short input, tail, end of input,
   exact length, alignment (impulse at lag 0), metadata, errors, abort;
2. 20 of 20 clean exits on every platform, RoFormer runs included;
3. Spleeter A/B: the Spleeter stems are byte-identical with the previous release, for every
   CPU variant CI can run.

Today CI proves none of them. The smoke test checks that the filter is registered; the
cpu-variant check skips because no model is present; the exit-hang test is Spleeter-only
and run by hand.

## What CI can and cannot execute

| platform | smoke runner | executes the binary |
|---|---|---|
| linux-x86_64 | ubuntu-latest | yes |
| windows-x86_64 | windows-latest | yes |
| darwin-x86_64 | macos-15-intel | yes |
| darwin-arm64 | macos-latest | yes |
| linux-aarch64 | ubuntu-latest | no (ELF header only) |
| freebsd-x86_64 | ubuntu-latest | no (ELF header only) |
| windows-aarch64 | windows-latest | no (PE header only) |

The three cross-exec platforms get the same checks through the manual suite
(`tests/tests.sh`, `tests/tests.ps1`) that `verify-rc` already requires on real hardware
for every platform. That is the same split #112's whisper checks use. "Green on all seven
platforms" therefore means: CI green on four, the manual suite green on the other three
before the RC box is ticked.

## Decisions

**D1. Run the stemsplit tag's own test suite, do not re-implement it.** `tests/run_tests.sh`
of tag `v1.1.0` already holds every check of the CI row, with the schedule, identity and
alignment oracles (`check_schedule.py`, `check_identity.py`) that took the stemsplit
project weeks to get right. Re-implementing them here would be a second, weaker copy of
the same oracle. The suite is fetched as the tag's source archive, pinned by SHA-256, and
run against the binary under test with `TINY_DIR` set (so a missing tiny file fails, not
skips) and `MODEL` set to the Spleeter file CI already fetches. The run passes only when
the suite's own summary line reports `failed 0`; a missing summary line is a failure.

**D2. The tiny models are a release asset, pinned by digest.** They are deterministic:
`tests/make_tiny_models.sh` of the tag regenerated all 65 files byte-identical (seed
20261014). Packed reproducibly (`tar --sort=name --mtime=<tag date> --owner=0`, `xz -9`:
23 MB for 334 MB of files, because the 49 refusal copies differ from the Mel model in one
place each) and attached to the ffmpeg-stemsplit `v1.1.0` release on Forgejo as
`stemsplit-tiny-models-v1.1.0.tar.xz`, sha256
`7b04652c855296e7d428ad5a130cf842e4da90eb16d2246fc7393284c42ea235`. Same host the build
already fetches the filter from. Not the models repository: there, a file absent from the
latest release means *withdrawn* (H10), and test fixtures have no place in a signed model
manifest. Generating them in CI was the alternative; it needs the converter's forty Python
packages on four platforms for a result that never changes.

**D3. One asset script, used by CI and by hand.** `tests/lib/stemsplit-assets.sh <platform>
<dir>` fetches everything by digest (the tag archive, the tiny tarball, the Spleeter model,
the previous release's binary for that platform) and prints the environment the checks
read. CI calls it in the smoke job; a contributor calls it once before the manual suite.
A download that is not what was pinned fails loudly. The same `fetch` shape as
`metal-gates`. One run at a time per directory: the checks write their corpus and work
files into it, and the reference binaries live under `ref/<platform>/`, so one machine can
hold several platforms' assets without them overwriting each other.

**D4. Three custom tests in a shared library, bash and PowerShell.** `tests/lib/stemsplit.sh`
and `tests/lib/stemsplit.ps1`, kept in step like `whisper.sh`/`whisper.ps1`, each
following `run_custom_test`'s protocol (0 pass, 2 skip with a `SKIP:` reason, else fail):

- `test_stemsplit_suite` — D1.
- `test_stemsplit_clean_exit` — 20 Spleeter runs and 20 tiny-RoFormer runs on the 4 s
  corpus file, each under a timeout; a run that outlives it, exits non-zero, or dies by a
  signal fails the check. The GPU series of `tools/ggml-variants/exit-hang-test.sh` stays a
  by-hand test: CI runners have no GPU.
- `test_stemsplit_spleeter_ab` — the stemsplit repository's own case list
  (`tests/ab_gate.sh`: 14 inputs × option sets, 32-bit float WAV, `-fflags +bitexact`),
  run on the binary under test and on the previous release's binary, every output compared
  with `cmp`. Repeated for every CPU variant the runner can run: automatic selection and the
  platform baseline (`x64` / `armv8.0`). The gate's sanity case (two option sets that must
  differ) is kept, so a pipeline that stops exercising the filter cannot pass.

**D5. CI fails on a skip.** The smoke job sets `STEMSPLIT_TEST_REQUIRED=1`, as the whisper
step does: a fetch that quietly stops supplying an asset must not leave the gates "passing"
by never running. The manual suite leaves it unset, so a machine without the assets skips
with a reason.

**D6. The suite runs under Git Bash on Windows.** `run_tests.sh` is POSIX sh; windows-latest
has Git Bash and Python. Every path handed to a filter option is relative (the binary runs
inside the work directory), because MSYS turns `/d/a/...` into `D:/a/...` and the colon
breaks avfilter's option parser. `python3` is a shim to `python` where only the latter
exists, and on macOS, which ships neither, `sha256sum` (five model-identity checks in the
suite) and `nproc` are shims over `shasum -a 256` and `sysctl`. The stemsplit maintainer's
`dev.sh` documents the same relative-path recipe.

**D1a. The suite comes from a commit on stemsplit's `main`, not the tag itself.** Run on
Windows, the tag's suite failed three checks that only work on Linux (reads
`/proc/<pid>/maps`, feeds ffmpeg through `/dev/stdin`, counts cores through Linux affinity),
and one more that broke under the relative-path recipe (`cp` of a relative tiny-model path
inside a `cd`). The handover left "how to run the same checks on the other platforms" to
this side; the owner chose fixing the suite upstream (tests only: the mapped assertion skips
where there is no `/proc`, `pipe:0` where the binary has it, cores counted per platform the
way `ss_physical_cores()` counts them, an absolute path for the copy). The fetcher pins that
commit's archive by digest and additionally asserts that `src/af_stemsplit.c` in it still
has the v1.1.0 digest, so the filter under test is provably the released one.

**D8. The build log names the filter it built.** `60-stemsplit.sh` logged the tag, byte
count and SHA-256 of the fetched `af_stemsplit.c`, but `init.sh` discards a component's
stdout and shows its log only on failure, so on every green build the line existed nowhere
a person could read it. The handover's first item ("compare the SHA-256 in your build log")
could not be done. Components can now pin lines through `/ffmpeg_build_pins.log`, which
`init.sh` prints (`📌 …`) after the component succeeds, on every build.

**D7. Trivy also scans the release PR.** The Trivy tool-status page shows every category as
"workflow runs failing" because the last master run (v1.0.44) concluded failure through
the non-gating metal-gates job. `security-scan` ran on master pushes only, so a scan could
never be seen before a release. It now also runs on the dev→master pull request from this
repository; the release PR's images are pushed under the commit SHA like master's, so
nothing else changes. Master pushes still scan.

## What this does not do

- No new check for the cross-exec platforms in CI. They cannot run the binary there; the
  manual suite covers them (see above).
- No Vulkan or Metal series in the clean-exit loop; no GPU on the runners.
- The RoFormer tiers with real weights (`MODEL_DIR`) stay skipped: 3.4 GB of models and
  40 minutes of work per minute of audio have no place in a smoke job.
- The darwin platforms cannot be executed on the build host; their first run is CI's.

## Verification

1. Every platform built locally with `STEMSPLIT_TAG=v1.1.0` (one at a time, as always).
2. linux-x86_64: the smoke script with the assets, inside an Ubuntu container with
   `python3-numpy`, exactly as the CI job runs it.
3. windows-x86_64: `smoke.ps1` on the build host.
4. The manual suite (`tests.sh`, `tests.ps1`) on the same two binaries, so the custom tests
   skip with a reason without the assets and pass with them.
5. Then dev, then the release PR, where CI runs the four executable platforms.
